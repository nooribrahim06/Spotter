# Prisma ORM

## What it is

Prisma ORM is Spotter's database access layer. It combines several related components:

| Component | Responsibility |
| --- | --- |
| Prisma Schema | Defines application models, database mappings, constraints, defaults, and native types. |
| Prisma CLI | Validates the schema, generates the client, manages migrations, and launches Studio. |
| Generated Prisma Client | Provides model-specific JavaScript/TypeScript query methods. |
| Driver adapter | Connects Prisma Client to the selected JavaScript database driver. |
| Prisma Studio | Provides a development UI for inspecting and editing database records. |

Prisma does not replace PostgreSQL. The schema describes how application models map to PostgreSQL, and Prisma Client generates and executes database operations through the configured adapter.

## How Spotter uses it

[`prisma/schema.prisma`](../../../backend/prisma/schema.prisma) selects PostgreSQL and generates a client into `backend/generated/prisma`:

```prisma
generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
}

datasource db {
  provider = "postgresql"
}
```

[`prisma.config.ts`](../../../backend/prisma.config.ts) supplies the schema path, migrations path, and `DATABASE_URL` used by Prisma tooling.

[`src/lib/prisma.js`](../../../backend/src/lib/prisma.js) creates the runtime client:

```js
const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const adapter = new PrismaPg(pool);

export const prisma = new PrismaClient({ adapter });
```

Exporting one shared client prevents every repository module from creating its own connection pool.

## The current User model

The `User` Prisma model maps to the PostgreSQL `users` table through `@@map("users")`. Selected mappings include:

| Prisma field | PostgreSQL representation | Purpose |
| --- | --- | --- |
| `id` | UUID primary key | Stable user identifier generated by `uuid()`. |
| `email` | `varchar(254)` with `UNIQUE` | Normalized account email. |
| `username` | `varchar(30)` with `UNIQUE` | Normalized public/login name. |
| `passwordHash` | `password_hash varchar(100)` | Bcrypt hash, never plaintext. |
| `role` | `UserRole`, default `USER` | Account authorization role. |
| `emailVerified` | `email_verified`, default `false` | Verification state. |
| `verifyToken` | Nullable `verify_token varchar(64)` | SHA-256 digest of the raw emailed token. |
| `verifyTokenExpiresAt` | Nullable `timestamptz(6)` | Token expiry instant. |
| `createdAt` | `timestamptz(6)`, default `now()` | Creation time. |
| `updatedAt` | `timestamptz(6)`, `@updatedAt` | Automatically updated modification time. |

`@map` changes a field's database-column name without making the JavaScript API use snake_case. `@@map` performs the equivalent mapping for the model/table name.

## How Spotter creates a user

[`src/modules/auth/user.repository.js`](../../../backend/src/modules/auth/user.repository.js) is the only current feature module that imports the shared Prisma client:

```js
const user = await prisma.user.create({
  data: {
    email,
    username,
    passwordHash,
    verifyToken,
    verifyTokenExpiresAt,
  },
  select: {
    id: true,
    email: true,
    username: true,
    createdAt: true,
    emailVerified: true,
  },
});
```

The `data` object becomes an insert. Database defaults fill omitted fields such as `id`, `role`, `emailVerified`, `createdAt`, and `updatedAt`.

The `select` object limits the returned shape and excludes `passwordHash` and verification-token data. This is defense in depth even though the current service returns only a message.

## Unique constraints and P2002

Email and username are marked `@unique`. Spotter inserts immediately instead of first performing a separate “does this exist?” query. This avoids a check-then-insert race because PostgreSQL is the final authority on uniqueness.

When an insert violates a unique constraint, Prisma reports the known request error code `P2002`. The repository translates it into an application error with `statusCode = 409`, which the controller forwards to Express.

For stronger type safety in future error handling, Prisma recommends checking that the caught value is a `PrismaClientKnownRequestError` before relying on `.code`.

## CLI commands currently defined

[`backend/package.json`](../../../backend/package.json) exposes:

```text
npm run db:validate   # Validate schema and configuration
npm run db:generate   # Regenerate Prisma Client
npm run db:studio     # Open Prisma Studio
```

Generation should run after relevant schema changes. The generated folder is build output and is ignored by Git in the current backend configuration.

## What it can do next

- Query accounts with `findUnique()` by ID, email, or username.
- Verify accounts with `update()` while clearing the token and expiry.
- Add profile, health, workout, coach, and session models with relations.
- Use nested writes for related records that must succeed together.
- Use `$transaction()` for multi-step atomic workflows.
- Add indexes based on real query patterns.
- Use `findMany()` with filtering, ordering, cursor pagination, and selected fields.
- Add migrations to version schema changes across environments.
- Add soft-delete or audit models where product requirements demand them.
- Use query logging and metrics during diagnosis, taking care not to expose secrets.

## Operational notes

- Keep one Prisma Client and one underlying pool per application process.
- Treat migrations as reviewed production artifacts; do not manually drift production schemas away from migration history.
- Select only fields a layer needs, especially around password and token data.
- Database constraints remain necessary even when Zod validates requests.
- Handle known errors deliberately, but do not expose raw Prisma errors or SQL details to clients.
- Close database resources during graceful shutdown and in test teardown.
- Validate `DATABASE_URL` before serving requests.
